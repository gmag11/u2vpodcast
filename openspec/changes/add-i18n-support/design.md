## Context

The SPA frontend (`frontend/`) is a Vue 3 + Pinia + vue-router + Tailwind app with 4 views and 16 components. Every user-facing string is hardcoded English: headings, buttons, placeholders, toast notifications, empty states, tooltips, and `aria-label`s. Dates are formatted with a hardcoded `toLocaleDateString('en-US')` in `EpisodeCard.vue`. Relative-age compact labels (`3h`, `5d`, `2w`) are generated by pure utility functions and are locale-neutral unit abbreviations.

There is no i18n dependency. The codebase already establishes a preference-persistence pattern in `frontend/src/stores/theme.ts`: read `localStorage`, fall back to a browser signal (`prefers-color-scheme`), apply on init. The `locale` store will mirror this exactly (`localStorage` + `navigator.language`).

The backend (Rust/actix-web) is out of scope: `CResponse::ko` payloads carry HTTP status strings (`"400 Bad Request"`), not human-readable sentences, and RSS feeds contain YouTube content data plus RSS-spec enum values (itunes `explicit`, `episode_type`). Nothing backend-side is user-facing UI text. Translation keys currently route through `result.message` fallbacks defined client-side.

Existing component tests (`AppHeader.test.ts` in `frontend/src/components/`, `HistoryView.test.ts` in `frontend/src/views/`) mount components with `[router, pinia]` plugins and assert English text; they must gain the i18n plugin and keep asserting with the `en` locale.

## Goals / Non-Goals

**Goals:**
- Support `en` (baseline) and `es` locales through vue-i18n v11 in composition mode.
- Detect, persist, and reactively switch locale on the existing `theme`-store pattern.
- Externalize 100% of user-facing strings: labels, buttons, placeholders, notifications, empty states, tooltips, `aria-label`s, date formatting.
- Add a language switcher in the header (desktop + mobile drawer).
- Keep the change frontend-only with no backend, DB, or config changes.

**Non-Goals:**
- Translating RSS feed content, YouTube titles/descriptions, or iTunes metadata (data, not UI).
- Localizing compact relative-age badges (`3h`, `5d`, `2w`, `1m`, `1y`) — unit abbreviations are treated as locale-neutral.
- Adding locales beyond `es` in this change; the infra must make future locales a matter of adding one JSON file.
- RTL layout support, URL-prefixed routes, or SSR.
- Backend-side Accept-Language negotiation or storing the user's locale in the database.

## Decisions

### D1: vue-i18n v11, composition API mode (`legacy: false`)
The project's single translation layer. Rationale: standard, maintained, provides pluralization (`1 episode` / `3 episodes`), interpolation (`Updated {age} ago`), locale-aware datetime formatting through `$d`, and per-message type inference.
- **Alternative considered:** Hand-rolled Pinia store + `computed` map over per-locale JSON. Rejected: we would re-implement pluralization, interpolation, and date formatting; ~150 strings and multilingual growth make a maintained library cheaper.

### D2: Static JSON locale bundles via `import`, registered in one `createI18n` call
`frontend/src/i18n/locales/en.json` and `es.json` are statically imported. At ~150 keys and two locales, code splitting is not a measurable win.
- **Alternative considered:** Dynamic `import()` of locale messages with `setLocaleMessage`. Rejected for now: adds async complexity with no benefit at this size; noted as a future optimization if locales multiply.

### D3: Locale store mirrors the theme store
`frontend/src/stores/locale.ts`: `locale` ref, `resolveInitial()` reads `localStorage` key `locale` (validated against `i18n.global.availableLocales`), falls back to `navigator.language` (`es`/`es-*` → `es`, everything else → `en`), `apply()` writes `localStorage`, sets `document.documentElement.lang`, and assigns `i18n.global.locale.value`. `init()` called from `main.ts` beside `theme.init()`.
- **Alternative considered:** Locale in the URL (`/es/...`) — rejected: the SPA is an auth-gated private tool with no SEO, so URL locale buys nothing and complicates the router.
- **Alternative considered:** Cookie-set locale readable by the backend for `Accept-Language` — rejected: no backend need exists.

### D4: Feature-scoped key naming
Keys group by screen/feature, not by component (e.g. `channels.create`, `episodes.refresh`, `player.pause`, `header.logout`, `age.tooltip`). Rationale: groups semantically related strings for translators, survives component refactors, and keeps `aria-label` variants next to their visible labels.
- **Alternative considered:** Component-scoped keys (`appHeader.logout`). Rejected: scatters semantically related strings and couples key namespaces to component names.

### D5: Locale-aware dates via vue-i18n `datetimeFormats`
`createI18n` receives `datetimeFormats` (`en` short/medium, `es` short/medium) and `useI18n()` exposes `$d`. `EpisodeCard`'s `formatDate` implementation replaces `toLocaleDateString('en-US')` with `d(episode.published_at, 'medium')`. Formatting stays reactive to locale changes.

### D6: Notifications translated at the call site
The notification store already accepts a rendered `message: string`; it displays whatever it receives. Call sites in views/components switch from literals (`notification.show('Channel updated', 'success')`) to `notification.show(t('channels.updated'), 'success')`. No store schema change.
- **Alternative considered:** Storing `key + params` in the store and translating inside `AppNotification.vue`. Rejected: adds indirection and makes dismissal/timing logic less transparent; call-site translation is idiomatic and keeps the store pure.

### D7: Language switcher in the header using radix-vue primitives
A compact dropdown (`DropdownMenu`/`DropdownMenuTrigger`/`DropdownMenuContent` from radix-vue, already a dependency) rendered in `AppHeader`'s actions cluster next to the theme toggle, visible at all screen widths (icon-only trigger on mobile). Each entry shows the autoglottonym (`English`, `Español`); no flag icons (a11y + neutrality). Selecting a language calls `locale.apply(code)`. The mobile drawer carries no duplicate control; the header-bar dropdown is the single language selector.
- **Alternative considered:** Single toggle button flipping `en`↔`es`. Rejected: becomes ambiguous the moment a third locale is added.
- **Alternative considered:** Duplicating the selector inside the mobile drawer. Rejected during implementation: on mobile the drawer is overlayed but the header bar stays visible, so a second control is redundant and clutters the drawer.

### D8: Language fallback and translation parity checking
`fallbackLocale: 'en'` ensures missing `es` keys degrade to English rather than raw keys. A unit test asserts every key in `en.json` exists in `es.json` (parity guard), preventing silent English fallbacks from creeping in.

### D9: Update tests with a shared mount helper
The two existing component tests gain the i18n plugin with the `en` locale. A small shared factory (e.g. `frontend/src/test/i18n.ts` exporting the i18n instance created with `en` only) is used so future tests reuse it and never depend on the developer's machine locale.

## Risks / Trade-offs

- **Existing tests assert English text** → test helper pins `en`, so assertions keep passing regardless of default detection; parity test covers `es`.
- **Translation drift** (missing `es` keys) → vue-i18n falls back to `en`; parity unit test fails CI-style on gaps.
- **Spanish strings longer than English** (layout overflow in buttons/dialogs) → translations reviewed on render; Tailwind classes adjusted only where a label genuinely overflows.
- **Locale flash on first paint** if detection differs from saved `localStorage` → store resolves synchronously before `app.mount`, same as theme; no async work on init.
- **`navigator.language` granularity** (`es-MX`, `en-GB`, …) → normalized to the language subtag before matching against `availableLocales`; unknown subtags fall back to `en` with the `fallbackLocale` safety net.

## Migration Plan

1. Add `vue-i18n` dependency; create `i18n/index.ts` with `en` + `es` bundles and `datetimeFormats`; register in `main.ts`.
2. Add `stores/locale.ts` and thread `locale.init()` into `main.ts` bootstrap.
3. Extract the full string inventory from the 4 views + 16 components into `en.json` (baseline) and translate into `es.json`.
4. Migrate components/views file-by-file (views first, then shared components), replacing literals with `$t`/`t()`.
5. Add the header language switcher (desktop + drawer).
6. Add the parity test and update the two existing tests with the i18n mount helper.
7. Run `pnpm typecheck && pnpm lint && pnpm test && pnpm build`; verify both languages by switching in the running SPA.

Rollback: revert the single frontend commit; no data migration, no backend changes, `dist/` rebuilds from old sources.

## Open Questions

- **Register vs informal Spanish**: defaulting to informal ("tú") matches the product's community tone; confirm during translation review.
- **Compact age badges**: treated as locale-neutral abbreviated units (non-goal). If a future locale wants full words ("5 days", "5 días"), that is a follow-up change — the badge values flow through a pure util that can be lifted into i18n keys later.
- **Persisting locale per browser vs per user**: this design persists per browser (localStorage), matching the theme store. Per-user persistence in the DB is a possible future enhancement, explicitly excluded here.
